Step 1 of 9 ⏱ 예상 소요 시간: 5분

개요: 에이펙스 자산운용의 자율형 AI 에이전트 보안 거버넌스

대규모 언어 모델(LLM) 기반의 자율형 AI 에이전트는 스스로 추론하고 워크플로를 오케스트레이션하며, 계좌 이체 API나 핵심 원장 데이터베이스 같은 엔터프라이즈 백엔드 도구를 직접 호출할 수 있습니다. 하지만 에이전트에게 백엔드 시스템에 대한 직접적인 네트워크 접근 권한을 부여하면 프롬프트 인젝션(Prompt Injection), 모델 환각(Hallucination), 비인가 고액 거래로 인한 심각한 보안 및 금융 컴플라이언스 리스크가 발생합니다.

또한 전통적인 IAM 권한 제어만으로는 "누가(어떤 서비스 계정이) 호출했는가"만 확인할 수 있을 뿐, "얼마를 어떤 맥락으로 이체하려 하는가"와 같은 페이로드 내부의 비즈니스 의미를 통제할 수 없으며, 에이전트 내부의 시스템 프롬프트 지시만으로는 우회 공격을 100% 막기 어렵습니다.

🏦 비즈니스 시나리오: 에이펙스 자산운용 (Apex Asset Management)

금융사인 에이펙스 자산운용은 고객이 대화만으로 간편 송금과 계좌 관리를 수행할 수 있도록 Gemini Enterprise Agent Runtime 기반의 대화형 뱅킹 에이전트(gemini-3.8-flash, Global 엔드포인트)를 도입했습니다.
금융보안 및 준법감시팀은 보이스피싱 및 고액 오송금 사고를 예방하기 위해, 에이전트 애플리케이션 코드를 수정하지 않고도 "1회 이체 금액이 100만 원(1,000 USD / amount <= 1000.0)을 초과하는 모든 송금 요청을 네트워크 경계에서 즉시 차단"하고 Cloud Logging에 감사 로그를 남기는 제로 트러스트 아키텍처를 구축하고자 합니다.

전체 시스템 아키텍처 및 트래픽 흐름 (3-Plane 분리 구조)

아래 아키텍처 다이어그램은 본 가이드에서 구축할 3개의 아키텍처 플레인(**Plane 1**: Gemini Enterprise 에이전트 런타임 환경, **Plane 2**: 고객 프로젝트 VPC 및 제어 플레인, **Plane 3**: Google 관리형 SGP 정책 평가 테넌트) 간의 상호작용과 5단계 트래픽 흐름을 보여줍니다.

[그림 1-1] Gemini Enterprise 에이전트와 Agent Gateway · SGP 기반 금융 보안 통제 아키텍처 (Plane 1 ~ Plane 3)
트래픽 흐름 단계 구성 요소 역할 및 상세 동작
1. 사용자 요청 금융 고객 김민준 (CUST005) ➔ Gemini Enterprise 에이전트 3-Turn 대화형 금융 요청 전달 (gemini-3.8-flash, Global API 엔드포인트 사용)
2. 호출 가로채기 Gemini Enterprise 에이전트 ➔ Agent Gateway (agent-egress) 아웃바운드 MCP 도구 호출(JSON-RPC 2.0)을 네트워크 경계에서 가로채기 및 TLS Inspection 복호화
3. 카탈로그 검증 Agent Registry ↔ Agent Gateway 허가된 MCP 도구 스키마(toolspec.json) 및 시스템 API Allowlist 확인 (roles/iap.egressor 검증)
4. 정책 심사 (PSC) Agent Gateway ➔ SGP 정책 엔진 (policy.internal.) Private Service Connect(PSC) 사설망을 통해 1회 이체 한도(100만 원 / USD 1000) 초과 여부 실시간 심사

⚡ 병렬 파이프라인 설계 안내

Gemini Enterprise Agent Runtime 컨테이너 빌드 및 샌드박스 프로비저닝은 백엔드에서 약 6~10분이 소요됩니다.

3-4. agent-egress 게이트웨이 매니페스트 작성 및 설정 항목 해설

AGENT_TO_ANYWHERE 거버넌스 경로, Agent Registry 연동, Network Attachment 및 policy.internal. 도메인에 대한 DNS 피어링 설정이 포함된 agent-gateway-vpc-egress.yaml 파일을 작성합니다.

Cloud Shell / Terminal — 명령어 3-4 (agent-gateway-vpc-egress.yaml 작성)
cat > ~/agent-gateway-sgp/agent-gateway-vpc-egress.yaml <<EOF
name: projects/${PROJECT_ID}/locations/${LOCATION}/agentGateways/agent-egress
protocols:
  - MCP
googleManaged:
  governedAccessPath: AGENT_TO_ANYWHERE
registries:
  - //agentregistry.googleapis.com/projects/${PROJECT_ID}/locations/${LOCATION}
networkConfig:
  egress:
    networkAttachment: projects/${PROJECT_ID}/regions/${LOCATION}/networkAttachments/agent-gateway-na
  dnsPeeringConfig:
    domains:
      - policy.internal.
    targetProject: ${PROJECT_ID}
    targetNetwork: projects/${PROJECT_ID}/global/networks/${NETWORK_NAME}
EOF

agent-gateway-vpc-egress.yaml 주요 설정 항목 상세 해설

필드 경로 설정값 아키텍처 역할 및 상세 설명
protocols [MCP] 게이트웨이가 Model Context Protocol(JSON-RPC 2.0) 메시지 구조를 파싱하여 도구 이름(method)과 인자(arguments)를 추출하도록 지정합니다.
googleManaged.governedAccessPath AGENT_TO_ANYWHERE 아웃바운드(Egress) 거버넌스 모드입니다. 에이전트에서 외부(Cloud Run, SaaS, 온프레미스 API 등)로 나가는 호출을 통제합니다. (반대로 외부에서 에이전트로 들어오는 인바운드 호출을 통제할 때는 ANYWHERE_TO_AGENT를 사용합니다.)
registries //agentregistry.googleapis.com/... 게이트웨이가 참조할 신뢰할 수 있는 서비스/도구 카탈로그(Agent Registry)의 리소스 경로입니다. 여기에 등록되지 않은 목적지는 기본 차단(Default Deny)됩니다.
networkConfig.egress.networkAttachment .../networkAttachments/agent-gateway-na 관리형 게이트웨이가 고객 VPC 내부 리소스(예: PSC 엔드포인트, 내부 ALB, 온프레미스 VPN/Interconnect)로 패킷을 내보낼 때 사용할 네트워크 연결점입니다.
networkConfig.dnsPeeringConfig domains: [policy.internal.] 게이트웨이가 policy.internal. 도메인의 IP를 찾을 때 퍼블릭 인터넷 DNS가 아닌 고객 VPC(apex-wealth-vpc)의 프라이빗 Cloud DNS에 질의하도록 DNS 피어링을 설정합니다.

Cloud Shell / Terminal — 명령어 5-3 (4대 시스템 엔드포인트 등록 및 IAP Egressor 부여)
ENDPOINTS=(
  "Gemini Enterprise Global API | https://aiplatform.googleapis.com"
  "Cloud Trace API | https://telemetry.googleapis.com"
  "Cloud Logging API | https://logging.googleapis.com"
  "Agent Registry API | https://agentregistry.googleapis.com"
)

for entry in "${ENDPOINTS[@]}"; do
  IFS="|" read -r name url <<< "$entry"
  name="$(echo "$name" | xargs)"
  url="$(echo "$url" | xargs)"
  service_id="$(echo "$name" | tr '[:upper:]' '[:lower:]' | tr -cd 'a-z0-9' | cut -c 1-40)"

  echo "Registering endpoint '${name}' (${url})..."
  res="$(gcloud alpha agent-registry services create "${service_id}" \
    --project="${PROJECT_ID}" \
    --location="${LOCATION}" \
    --display-name="${name}" \
    --endpoint-spec-type=no-spec \
    --interfaces=url="${url}",protocolBinding=JSONRPC \
    --format="value(registryResource)" 2>&1)" || \
  res="$(gcloud alpha agent-registry services describe "${service_id}" \
    --project="${PROJECT_ID}" \
    --location="${LOCATION}" \
    --format="value(registryResource)" 2>/dev/null || true)"

  ep_id="$(echo "${res}" | grep -oE 'agentregistry-[0-9a-f-]+$' | head -n 1 || true)"
  if [[ -n "${ep_id}" ]]; then
    echo "Binding roles/iap.egressor on endpoint ${ep_id}..."
    for MEMBER in "${AGW_SA}" "${RE_SA}" "${AGENT_PRINCIPAL}"; do
      gcloud alpha iap web add-iam-policy-binding \
        --resource-type=agent-registry \
        --endpoint="${ep_id}" \
        --region="${LOCATION}" \
        --project="${PROJECT_ID}" \
        --member="${MEMBER}" \
        --role="roles/iap.egressor" \
        --quiet >/dev/null 2>&1 || true
    done
  fi
done

왜 SGP 연결에 PSC와 프라이빗 DNS를 사용합니까?

SGP 정책 엔진은 Google이 관리하는 별도의 보안 테넌트 프로젝트에서 실행됩니다. 금융권과 같은 엔터프라이즈 환경에서는 도구 호출 페이로드(고객 계좌번호, 송금 금액 등 민감 데이터 포함)가 공인 인터넷(Public Internet)을 경유해서는 안 됩니다. 아래 다이어그램과 같이 DNS 피어링 + 프라이빗 DNS + PSC 엔드포인트를 결합하면 모든 정책 심사 트래픽이 Google 내부 백본 사설망 안에서만 안전하게 처리됩니다.

🏢 자사 인프라 적용 시 핵심 설계 포인트 (VPC Peering 대비 PSC의 이점)

전통적인 VPC Network Peering은 양측 VPC의 전체 서브넷 대역이 노출되고 전이적 라우팅(Transitive Peering) 제한 및 IP 대역 충돌 문제가 발생할 수 있습니다. 반면 Private Service Connect(PSC)는 고객 서브넷 내의 단일 IP 주소(${PSC_IP}) 하나만 소비하여 단방향(Consumer ➔ Producer)으로 SGP 엔진에 연결하므로, 복잡한 금융권 허브-앤-스포크(Hub-and-Spoke) 네트워크에서도 IP 충돌 없이 안전하게 도입할 수 있습니다.

8-1. SGP 인가 확장 (sgp-authzextension) 등록

게이트웨이가 외부 인가 심사관(Callout)으로 호출할 대상을 policy.internal로 지정하고, failOpen: false(장애 시 차단 원칙)로 설정된 SGP 인가 확장(sgp-authzextension)을 등록합니다.

Cloud Shell / Terminal — 명령어 8-1 (sgp-authzextension 등록)
cd ~/agent-gateway-sgp
source customer-env.sh
[[ -f .env.runtime ]] && source .env.runtime

ACCESS_TOKEN="$(gcloud auth print-access-token)"
curl -fsS -X POST \
  "https://networkservices.googleapis.com/v1beta1/projects/${PROJECT_ID}/locations/${LOCATION}/authzExtensions?authzExtensionId=sgp-authzextension" \
  -H "Authorization: Bearer ${ACCESS_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "service": "policy.internal",
    "authority": "policy.internal",
    "failOpen": false,
    "loadBalancingScheme": "LOAD_BALANCING_SCHEME_UNSPECIFIED"

  • "service": "policy.internal" 및 "authority": "policy.internal": Step 7에서 프라이빗 Cloud DNS에 등록한 SGP PSC 엔드포인트 도메인을 가리킵니다.
  • "failOpen": false: 금융 거래와 같은 고위험 워크로드에서 필수적인 Fail-Closed(장애 시 차단) 설정입니다. 만약 네트워크 설정 오류나 정책 엔진 장애로 심사 결과를 받을 수 없는 경우, 요청을 우회 통과시키지 않고 안전하게 차단합니다.

9-3. Cloud Logging에서 SGP 시맨틱 거버넌스 감사 로그 조회 및 심층 분석

SGP 정책 엔진은 에이전트의 도구 호출을 심사할 때마다 프로젝트의 logs/semantic-governance-policy 로그 스트림에 상세 감사 로그를 남깁니다. 아래 명령어를 실행하여 실제 도구 호출 판정 감사 로그(jsonPayload.verdict:*)를 조회합니다.

Cloud Shell / Terminal — 명령어 9-3 (SGP 감사 로그 필터링 조회)
cd ~/agent-gateway-sgp
source customer-env.sh

gcloud logging read \
  "logName=\"projects/${PROJECT_ID}/logs/semantic-governance-policy\" AND jsonPayload.verdict:*" \
  --project="${PROJECT_ID}" \
  --limit=5 \
  --format=json
🔍 참고: 왜 필터에 AND jsonPayload.verdict:* 조건을 추가하나요? (하트비트 로그 vs 감사 로그)

logs/semantic-governance-policy 로그 스트림에는 도구 호출 시 기록되는 판정 감사 로그(jsonPayload.verdict: "ALLOW" | "DENY") 외에도, SGP 런타임 노드(node_id: "sgp-runtime")가 30초 주기로 정책 동기화 및 파드 정상 가동 상태를 보고하는 컨트롤 플레인 하트비트 로그("totalPods": 2, "podDistributionsPercentages": {"...": 100})가 함께 기록됩니다.
따라서 위 명령어처럼 AND jsonPayload.verdict:* 조건을 추가하면 주기적인 하트비트 상태 로그를 제외하고, 실제 에이전트 도구 호출에 대한 ALLOW / DENY 감사 로그만 정확하게 추출할 수 있습니다.

실제 Cloud Logging에 기록된 Turn 3 (DENY) 감사 로그 JSON 구조

JSON — Turn 3 ($2,000 송금 차단) 감사 로그 출력 예시
{
  "jsonPayload": {
    "verdict": "DENY",
    "userFacingDenialMessage": "The requested transfer amount of 2000 USD exceeds the maximum allowed limit of 1000 USD stipulated by the 'High Value Transfer Limit' policy.",
    "evaluations": [
      {
        "actionName": "Banking_MCP_Server_transfer_to_phone",
        "toolName": "Banking_MCP_Server_transfer_to_phone",
        "verdict": "DENY",
        "rationale": "The requested transfer amount exceeds the maximum allowed limit stipulated by the 'High Value Transfer Limit' policy."
      }
    ],
    "token_usage": 3164
  },
  "logName": "projects/YOUR_PROJECT_ID/logs/semantic-governance-policy",
  "receiveTimestamp": "2026-10-14T01:30:12.418291042Z"
}

SGP 감사 로그 핵심 필드 상세 해설

JSON 필드 경로 값 예시 보안 감사 및 컴플라이언스 의미
jsonPayload.verdict "ALLOW" 또는 "DENY" SGP 정책 엔진이 해당 요청에 대해 내린 최종 인가 판정입니다. Turn 2(amount: 50)는 ALLOW, Turn 3(amount: 2000)는 DENY가 기록됩니다.
jsonPayload.userFacingDenialMessage "The requested transfer amount of 2000 USD exceeds..." 차단(DENY) 시 Agent Gateway를 통해 에이전트에게 반환되는 거부 사유 메시지입니다. 에이전트는 이 메시지를 바탕으로 고객에게 차단 이유를 친절하게 안내합니다.
jsonPayload.evaluations[].toolName "Banking_MCP_Server_transfer_to_phone" 심사 대상이 된 구체적인 MCP 도구 식별자입니다.
jsonPayload.evaluations[].rationale "The requested transfer amount exceeds the maximum allowed limit..." SGP 정책 평가 모델이 왜 해당 도구 호출을 허용하거나 차단했는지 설명하는 자연어 판단 근거(Audit Rationale)입니다. 금융 감독 감사 시 핵심 증적 자료로 활용됩니다.
jsonPayload.token_usage 3164 시맨틱 거버넌스 정책 평가를 수행하는 데 소비된 토큰 수입니다.
🏢 자사 인프라 적용 시 핵심 설계 포인트 (SIEM 연동 및 금융 컴플라이언스 감사)

기업 보안 운영 센터(SOC)에서는 Cloud Logging의 Log Sink(로그 라우터) 기능을 사용하여 logName="projects/.../logs/semantic-governance-policy" AND jsonPayload.verdict:* 로그를 BigQuery(장기 금융 감사 보관용) 또는 Google Security Operations (Chronicle) / 사내 SIEM으로 실시간 스트리밍할 수 있습니다.
특히 짧은 시간 내에 jsonPayload.verdict="DENY" 판정이 반복 발생하는 세션이나 에이전트 ID에 대해 Cloud Monitoring 로그 기반 알림(Log-based Alerting)을 설정하면, 비정상적인 프롬프트 인젝션 시도나 에이전트 오작동을 즉시 탐지하고 보안 담당자에게 경보를 발송할 수 있습니다.
